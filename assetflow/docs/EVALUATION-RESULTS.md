## 결과

| 지표 | 개발셋 (8건) | 최종셋 (16건) |
|---|---|---|
| 처리 경로 정확도 | 1.00 | **0.88** (14/16) |
| 대상 자산 정확도 | 1.00 | 0.88 (14/16) |
| 근거 규정 정확도 | 1.00 | 0.81 (13/16) |
| 3회 반복 분산 | 0 | 0 |

**개발셋 1.00과 최종셋 0.88의 차이 0.12가 개발셋 점수의 거품이다.** 개발셋은 프롬프트와 코드를 고치면서 본 것이므로 성능 근거가 아니다.

분산이 0이므로 이 차이는 실행 운이 아니다.

## 구성 비교 — 규정을 프롬프트에 넣는가

| 구성 | 경로 정확도 | 근거 정확도 |
|---|---|---|
| 규정 top-3 포함 | 0.62 | 0.75 |
| 규정 제외 | 0.92 | 0.12 |

decide 노드 v6 기준, 개발셋 8건 3회. **규정 본문이 판정을 방해하고 있었다.**

`INSPECTION-REQUIRED`의 "담당자 점검이 선행되어야 한다"를 모델이 "정보 부족"으로 읽어 `need_review` 대신 `need_info`를 골랐다. 규정을 빼면 경로는 좋아지지만 인용이 불가능해진다.

v7에서 입력을 `판정_입력`·`인용_후보_규정` 두 블록으로 나눠 해결했다. v11에서는 경로 판정 자체를 코드로 옮겨 이 상충이 사라졌다.

## 비용과 지연

`node_trace` 48회 실행 기준.

| 노드 | 평균 | p95 | 최대 |
|---|---|---|---|
| decide (LLM) | 1,277ms | 1,544ms | 2,588ms |
| retrieve (임베딩) | 260ms | 411ms | 778ms |
| propose (DB) | 3ms | 4ms | 4ms |
| load (DB) | 1ms | 3ms | 5ms |

| 항목 | 값 |
|---|---|
| 요청당 LLM 비용 | **$0.000227** |
| 프롬프트 토큰 평균 | 1,312 |
| 출력 토큰 평균 | 50 |
| 상한 $5 기준 처리 가능 건수 | 약 22,000건 |

**LLM 호출이 전체 지연의 83%다.** DB 작업은 합쳐서 5ms 미만이다.

프롬프트가 1,312토큰으로 유지되는 이유는 검색이 규정을 3개로 좁히기 때문이다. 규정이 100개가 되어도 이 크기는 유지된다.

## 실패 사례

### 자산 어휘 사전의 한계 — 2건

| id | 요청문의 표현 | 결과 |
|---|---|---|
| FIN-15 | "액정" | `need_info`로 거부 |
| FIN-16 | "허브" | `need_info`로 거부 |

`verify_target`이 쓰는 `ASSET_TERMS`는 손으로 쓴 사전이다. 여기 없는 말로 자산을 가리키면 **정당한 선택도 기각된다.**

이 검증은 의도된 것이다 — LLM이 요청자가 말하지 않은 자산을 추론해 고르는 것을 막는다(개발셋 DEV-06에서 실제로 발생). 대가로 어휘 폭이 사전에 묶인다.

**세 지표가 동시에 떨어진 것은 원인이 셋이어서가 아니라 하나여서다.** 대상을 못 정하면 경로·대상·인용이 함께 틀린다.

### 규정 검색 실패 — 1건

| id | 경로 | 인용 |
|---|---|---|
| FIN-12 | `escalate` (정답) | `[]` (기대 `COST-LIABILITY`) |

같은 주제의 두 문장인데 결과가 갈렸다.

```
"노트북을 떨어뜨렸습니다. 제가 변상해야 하는지…"
 → REPLACE-FAULTY 0.743 / OWNERSHIP 0.774 / REPLACE-STOCK 0.774   (COST-LIABILITY 없음)

"휴대폰을 실수로 밟아서 깨졌는데 수리비를…"
 → REPLACE-FAULTY 0.679 / COST-LIABILITY 0.742 / INSPECTION-REQUIRED 0.746
```

6개 규정의 거리가 전부 0.68~0.78에 몰려 있어 순위가 불안정하다. 규정이 적고 문체가 비슷해 임베딩 공간에서 잘 갈라지지 않는다.

**경로는 맞았고 인용만 비었다.** `pick_policy_refs`가 "맞는 주제가 후보에 없으면 아무거나 고르지 않는다"로 설계된 대로 동작한 결과다. 엉뚱한 규정을 인용하는 것보다 비우는 쪽이 낫다는 선택이었고, 그 선택이 점수로는 손해로 나타난다.

## 한계

**이 숫자로 주장할 수 없는 것을 먼저 적는다.**

1. **최종 평가셋을 에이전트가 작성했다.** 시스템의 약점을 아는 상태에서 만든 것이므로 독립 평가가 아니다. 내부를 모르는 사람이 다시 작성해야 일반화 성능이 된다.
2. **표본이 16건이다.** 실패 3건의 차이는 사례 1~2건으로 뒤집힌다. 신뢰구간을 낼 규모가 아니다.
3. **재고 부족(`REPLACE-STOCK`) 경로를 측정하지 못했다.** 시드에서 재고가 미처리 수량보다 항상 커서, 수량을 늘리면 재고 부족 전에 수량 초과에 먼저 걸린다.
4. **합성 데이터다.** 임직원·자산·규정 전부 가상이다. 실제 사내 요청문의 분포와 다르다.
5. **`escalate` 판정만 LLM에 남아 있고 따로 검증되지 않는다.** 나머지 경로는 값 비교라 결정적이지만, 귀책 주제 판단은 오판해도 잡을 장치가 없다.
6. **B1(역할 분리 구성) 비교를 하지 않았다.** 최소판 범위 밖이다.
7. **사람 수정량을 측정하지 않았다.** 담당자가 처리안을 얼마나 고치는지는 실사용 없이는 잴 수 없다.
8. **개발용 DB 비밀번호가 `infra/.env`와 `ai-service/.env` 두 곳에 있다.** 둘 다 커밋되지 않지만 값이 두 곳에 있으면 갈라진다. 운영이라면 secret store 한 곳에서 양쪽이 읽어야 한다.
