# AssetFlow 데이터 확보 계획

## 원칙

실행 데이터는 자체 생성하고, 공개 사례는 상황의 다양성을 파악하는 참고로 사용한다. 실제 고객 상담·주문 원장은 필요하지 않다. 대규모 수집보다 정책·주문·문의·정답 간 일관성이 우선이다.

## 확장 규모 — 최소판 통과 후

| 데이터 | 목표 | 확보 방식 |
|---|---:|---|
| 가상 자산 모델 | 20~30개 | 직접 구성 |
| 지급 이력 | 약 100건 | 재현 가능한 생성 규칙 |
| 지급 항목·점검 상태·자산 재고 | 지급 이력과 연결 | 관계·상태 제약에 맞게 생성 |
| 사내 자산 규정 | 10~15개 조항 | 가상 운영 규정과 판단표 직접 작성 |
| 개발 요청문 | 약 60건 | 시나리오 작성 및 문장 변형 |
| 최종 평가 요청문 | 약 40건 | 별도 시나리오 작성·검수 |
| 시스템 검증 | [TRACEABILITY.md](TRACEABILITY.md)의 필수 항목 전체 | 최소판부터 적용; 확장 전용 게이트는 별도 표시 |

최소판은 자산 모델 5~10개·지급 이력 약 20건·규정 10~15개·개발16/평가16건을 먼저 검수한다. 시스템 검증은 표본 확대와 무관하게 최소판부터 필수 목록 전체를 적용한다. 위 표의 나머지 수량은 확장 목표이며 수집·생성 완료 수량이 아니다. 실제 사람 이름·주소·연락처·사번은 포함하지 않는다.

## 1. 공개 사례 유형 조사

사내 IT 지원 업무에서 흔한 상황 유형(장비 고장, 오지급, 지급 지연, 귀책 불명, 정보 부족)을 참고한다. 공개된 IT 서비스 데스크 사례나 일반적인 운영 관행을 상황 유형 파악에만 사용한다.

- 외부 사례의 판단을 현재 가상 규정의 정답으로 사용하지 않는다.
- 수작업으로 소수 사례를 검토해 출처 URL, 게시일, 상황 유형, 필요한 확인 항목을 기록한다.
- 외부 원문이나 회사 내부 자산을 복제하지 않는다. 독립적인 가상 상황으로 작성한다.
- 공개 문서를 서비스 검색 코퍼스로 포함하려면 해당 자료의 이용조건과 출처 표시 범위를 별도 확인한다. RAG 코퍼스는 자체 작성한 가상 규정만 사용한다.

## 2. 규정과 판단표

요청 종류, 지급/전달 상태, 요청 수량, 이전 처리량, 교체 재고, 점검 상태를 입력으로 정의한다. 결과는 추가 질문/처리안/담당자 이관이다.

규정에는 ID, 버전, 적용일, 조건, 예외, 필요한 정보, 허용 행동을 기록한다. 어떤 기준일로 규정을 선택할지 명시하고 근거가 불명확하면 이관한다. 테스트용 가상 규칙이라는 점을 표시하며 법적 준수를 주장하지 않는다.

MVP의 금액 계산은 지급 항목별 자산 취득가와 기처리 수량을 기준으로 한다. 감가상각·귀책 비율 배분 등 미지원 계산은 자동 추정하지 않고 이관한다.

## 3. 실행 데이터 생성

- 고정 시드와 생성 설정을 기록한다.
- 자산 모델 → 지급 이력/지급 항목 → 전달·점검 → 재고 → 기존 등록 순서로 관계를 생성한다.
- 요청 수량 ≤ 미처리 수량, 청구액 ≤ 자산 취득가 등 관계를 검증한다.
- 정상 생성 데이터와 의도적으로 모순을 넣은 실패 시나리오를 구분한다.
- 가상 임직원 ID와 지급 소유 관계를 두어 접근 검증 사례도 만든다.
- 업무상 존재할 수 없는 조합은 생성 오류로 처리하고, 설명 가능한 예외만 테스트 데이터로 유지한다.

## 4. 문의와 정답 작성

시나리오를 먼저 작성하고 짧은 말투·오타·감정 표현·복수 요청 등으로 변형한다. LLM은 표현 다양화에만 보조 사용한다. 정답은 정책 판단표와 사람이 검수하며 에이전트 출력으로 자동 확정하지 않는다.

사례별 필드: case_id, scenario_family, assignment_snapshot, policy_version, user_message, expected_route, required_questions, evidence_ids, allowed_actions, expected_amount, prohibited_actions, provenance, reviewer_status.

개발/평가는 상황군 단위로 분리한다. 같은 상황의 문장 변형은 한쪽에만 둔다. 최종 평가 정답은 런타임 저장소와 검색 인덱스 밖에 보관한다.

## 5. 검수와 버전 관리

- 모든 평가 사례를 사람이 검수한다. 해결되지 않은 사례는 점수 산정 전에 보류 목록으로 분리한다.
- 데이터 버전, 규정 버전, 임베딩 모델, 생성 시드, 출처, 변경 이유를 기록한다.
- 최종 평가를 보고 수정하면 개발셋에 편입한 사실을 남기고 새로운 최종셋 또는 평가 노출 사실을 보고한다.
- 유형별 할당은 검증용 균형 설계이며 실제 사내 요청 발생 비율로 해석하지 않는다.

## 완료 기준

데이터를 재생성할 수 있고 관계 검증이 통과한다. 개발/평가 분리와 검수 기록이 있으며 원문 수집, 자체 작성, 합성 생성의 출처가 구분된다. 외부 데이터 공급을 기다리지 않고 최소 흐름을 개발할 수 있다.
