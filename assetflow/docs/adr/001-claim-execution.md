# 001. Transactional claim execution and inventory allocation

Date: 2026-09-09
Status: Accepted. The inventory decision is superseded by ADR-002; the server-issued stable execution key, PostgreSQL authority, and single FastAPI/PostgreSQL transaction boundary remain in force.

Update 2026-10-06: [ADR-002](002-stock-reservation.md) replaced the no-reservation inventory decision and is implemented and locally verified. Approval now creates a quantity reservation. The other three decisions remain in force.

## Context

AssetFlow is a simulated internal IT asset request workflow (domain changed 2026-09-11; the transactional decisions below are unaffected). Inventory timing, request identity, approval validity and recovery are architecture decisions, not unresolved shop policy. Current available engineering hours are unknown, so the minimum design uses one FastAPI application and one PostgreSQL transaction boundary. No separate service or external procurement/dispatch mutation is required.

## Options considered

| Decision | Alternative | Proposed choice and trade-off |
|---|---|---|
| Inventory | Reserve while awaiting approval, with expiry/release jobs | No reservation while waiting; allocate atomically at execution. Simpler recovery, but approval does not guarantee stock |
| Execution identity | New key for every retry | Stable server-issued identity for a claim/proposal-version/action tuple; retries reuse it |
| State ownership | Graph checkpoint is the transaction ledger | PostgreSQL business records are authoritative; checkpoints reference them and reconcile after restart |
| Service boundary | Separate asset service plus distributed reconciliation | Local simulated tool and request writes share a DB transaction; cross-service execution deferred |

## Proposed decision

- request_id identifies the employee's case, not a model run. Messages carry a separate request identity. Repeated messages do not themselves authorize an action.
- proposal_version is immutable. Approval references that version and its payload digest. A changed proposal requires new approval. Authenticated IT operator identity and server-verified approval permission are required (SYS-17a/17b); the requester's consent to an alternative model is separate from operator approval.
- execution_key is generated by the server and bound uniquely to request_id/proposal_version/action. Store the payload digest. Same key and same payload returns the existing outcome; same key with different payload is rejected.
- Different keys do not bypass quantity limits. Assignment-item available quantity is checked atomically and allocated to the accepted request. A still-open allocation cannot be allocated again, including across separate request IDs.
- The execution transaction checks authorization, current approval, relevant policy version, unprocessed quantity and available stock; allocates stock/request quantity; inserts the simulated dispatch and execution outcome; and commits together. Lock ordering is consistent (assignment item, then stock). Concurrent depletion rejects or replans the losing action without a negative balance.
- Superseded inventory rule: ADR-002 now reserves stock and assignment-item quantity when approval commits. Execution consumes that reservation. It is still a simulated dispatch, not physical handover.
- A timeout after commit is resolved by looking up execution_key. No second mutation is issued with a new key. A transaction rolled back before commit can be retried under the same key after validation. Unreachable DB means outcome unknown, not success or definite failure.
- Approval rejection creates no dispatch record. Workflow states include needs_information, needs_review, awaiting_approval, rejected, ready_to_execute, outcome_unknown and registered. Graph state is synchronized from the business outcome rather than treated as proof of execution.

Update from ADR-002 step 6: new code no longer writes `outcome_unknown`. A database outage cannot be recorded in that same database, so the API returns a temporary unknown response and reconciles through the execution ledger after connectivity returns. The enum value remains only for existing rows and migration compatibility.
- Cost claims remain a proposal/escalation path in minimum scope. No simulated claim-ledger writes are exposed until liability and timing policies are accepted and SYS-05b passes. Requests must not be marked charged merely because a proposal exists.

## Open business policy decisions

Replacement cycle, inspection acceptance, damage liability and claim timing remain business decisions. The minimum demo uses pre-inspected eligible replacements; missing policy facts escalate. Policy IDs/versions/effective-date fields are architecture, while their content and applicability rules require business review.
